# 发布流水线（第 3 步）

**日期**: 2026-11-25
**状态**: 已实现，等待 CI 在 PR 上演练；未真机验证

## 目标

1. Windows 和 Linux 也能在应用内检查并安装更新。
2. 发布版有日志可查，用户反馈「下载失败」时能看到原因。
3. 发布流程不再因为版本号没改、文件漏传而出错。

## 应用内更新

更新器按 `{系统}-{架构}-{安装包类型}` 在 `latest.json` 里找自己。原来清单里只有 macOS 的三个键，Windows 和 Linux 找不到，直接报错。

- 构建时把更新器要用的文件一起上传：Windows 的 `-setup.nsis.zip` 与签名，Linux 的 `.AppImage.tar.gz`、`.deb` 与各自的签名。
- 清单新增 `windows-x86_64-nsis`、`linux-x86_64-appimage`、`linux-x86_64-deb`。
- Linux 装 deb 需要管理员权限，更新器依次尝试 pkexec、图形化密码框、终端 sudo，应用侧不需要额外处理。

## 日志

- 使用官方 `tauri-plugin-log`，写到系统分配给应用的日志目录，单个文件上限 500 KB，保留最近 3 份。
- 应用自己的日志记到 debug 级别，依赖库只在警告及以上才记。
- 记录：每页抓取概况、被微博拒绝的请求（状态码、路径、响应前 200 字）、重试、长文与图片失败、下载结果、续传起点、AI 画像分析失败的原因。
- 不记录 Cookie 的值，登录窗口只记录拿到了几个 Cookie。
- 崩溃前先写一条 panic 日志。发布版是 `panic = "abort"`，进程会直接退出，这条日志是唯一线索。
- 错误页新增「打开日志文件夹」。

## 发布流程

- 推送 `main` 仍然自动发布，版本号取自 `package.json`。
- `scripts/release.mjs check-versions`：四处版本号必须一致，CI 的第一个作业就检查。
- 推送 `main` 时先检查同名 Release 是否已存在，已存在直接失败，不会覆盖已发布的文件。
- `scripts/release.mjs prepare`：改名、生成不带版本号的安装包副本、写 `latest.json`。任何一类文件缺失或重名都失败。
- 每个 PR 都用同一个脚本演练一遍发布（`Assemble release (rehearsal)`），结果作为产物上传供核对。
- 官网的下载链接改为不带版本号的固定文件名，不会因为忘了改版本号而 404。

## 已知限制

- Windows、Linux 的应用内更新没有真机验证，只验证到「产物存在、清单正确」。
- 日志文件的实际位置和内容没有在真实应用里看过。
- 没有 Linux rpm 包；macOS 仍然没有代码签名和公证。
